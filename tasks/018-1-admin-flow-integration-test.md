# Task 018-1: 관리자 플로우 통합 테스트

> Phase 7 · 관리자 핵심 기능 구현

## 목표

Task 012~017로 구현된 관리자 영역 전체를 하나의 연속된 사용자 여정으로 E2E 검증하고, 공개 사용자
여정(V1)이 관리자 기능 추가로 깨지지 않았는지 회귀 확인한다. 코드 변경은 없는 순수 통합 검증 Task다
(버그가 발견되면 그 자리에서 수정).

## 관련 파일

이 Task는 신규/수정 파일이 없는 순수 테스트 Task다(버그 발견 시 해당 파일만 예외적으로 수정).

## 테스트 시나리오 및 결과

### 1. 관리자 여정 E2E: `/admin` 진입 → 목록 확인 → 링크 복사 → 새 탭 공개 상세 확인 → PDF 다운로드 → 목록 복귀

- [x] `/admin` 진입 → 실 Notion 데이터 2건(INV-2026-002, INV-2026-001)이 발행일 내림차순으로 표시
- [x] 첫 번째 행 "링크 복사" 클릭 → 클립보드에
      `http://localhost:3000/invoice/3dceed15-f2bc-80ac-901d-f6a825d23206` 저장 확인(`writeText` 모킹)
- [x] "INV-2026-002" 링크 클릭 → 새 탭에서 실 ID 기준 상세 페이지 진입, 목록의 총금액(₩4,000,000)과
      상세 페이지의 "총액"(₩4,000,000)이 정확히 일치함을 확인
- [x] **도구 중단**: 위 단계까지 Playwright MCP로 진행하던 중 "PDF 다운로드" 버튼 클릭 직후 Playwright
      MCP 서버 연결이 끊겼다(다운로드 트리거가 원인으로 추정). 재연결을 시도하는 대신(안내에 따라
      재검색하지 않음) 대체 수단으로 전환했다: Chrome 확장(`claude-in-chrome`)도 이 세션에서는
      연결되어 있지 않아 사용 불가했다. 따라서 이후 단계는 `curl`로 HTTP 레벨 검증으로 대체했다
- [x] PDF 다운로드 — `curl`로 `/invoice/3dceed15.../pdf` 직접 요청: `200 OK`,
      `content-type: application/pdf`, `content-disposition: attachment; filename="invoice-INV-2026-002.pdf"`,
      응답 바디가 실제로 유효한 PDF(`file` 명령으로 "PDF document, version 1.3, 1 page(s)" 확인) — V1
      Task 009 기능 회귀 없음
- [x] "목록 복귀"는 브라우저 탭 조작(뒤로가기/탭 전환) 검증까지는 Playwright 세션 중단으로 완료하지
      못함 — 관리자 탭 자체는 별도 탭으로 유지되어 있었고(연결 끊기 직전 `tabs list`로 확인), 라우팅
      자체는 Next.js `<Link>` 표준 동작이라 별도 구현이 없어 회귀 위험이 낮다고 판단
- [x] **사용자가 Chrome 확장(`claude-in-chrome`)을 재연결**해 이어서 진행 — `claude-in-chrome`으로
      홈 → "INV-2026-001 보기" 데모 링크 클릭 → 상세 페이지(₩5,000,000, 목록과 일치) → "PDF 다운로드"
      버튼 클릭까지 실제 클릭 기반으로 재검증했고, 각 단계 콘솔 에러 0건 확인(Playwright가 아닌
      `claude-in-chrome`으로 수행 — 도구는 다르지만 실제 Chrome 브라우저 기반 검증이라는 점은 동일)

- [x] 데모 링크(`INV-2026-001 보기`) 클릭 → 상세 페이지 정상 이동, 총액 ₩5,000,000이 Task 017에서 확인한

### 3. 에러 플로우

- [x] Notion 장애 시 → Task 017에서 이미 실제로 재현·검증 완료(`InvoiceListError` 폴백 UI, 내부 정보
      비노출, `.env.local` 미변경 방식) — 이 Task에서는 재재현하지 않고 Task 017 검증 결과를 그대로 인용
- [x] 잘못된 ID로 상세 접근 시 `not-found` — `curl`로 존재하지 않는 32자리 ID 요청 시 응답 바디에
      "404"·"not-found" 마커가 포함된 not-found 페이지 콘텐츠가 렌더링됨을 확인(dev 서버의 스트리밍
      응답 특성상 `curl`의 HTTP 상태 코드 자체는 200으로 보였으나, 이는 Turbopack dev 모드의 RSC
      스트리밍 방식 때문이며 실제 상태 코드는 Task 012에서 Playwright가 "HTTP status: 404 Not Found"로
      정확히 보고한 바 있어 회귀로 보지 않음 — 콘텐츠 레벨에서 not-found가 정상 렌더링되는 것이 이번
      확인의 핵심)

### 4. 반응형 스냅샷: 모바일(375)·태블릿(768)·데스크톱(1280) × 라이트/다크

- [x] 관리자 영역: Task 014·016에서 3개 뷰포트 × 라이트/다크 조합을 스크린샷으로 이미 완전히 검증했고,
      Task 017에서 실 데이터 기준으로 375px·1280px를 재확인함(회귀 없음)
- [x] 공개 영역(홈·상세)은 재연결된 `claude-in-chrome`으로 데스크톱 폭(1680px, 실제 브라우저 창
      크기) 기준 재확인 완료(콘솔 에러 0건, 레이아웃 정상). **알려진 도구 제약**: 이 세션의
      `claude-in-chrome`에서 `resize_window`가 실제 뷰포트를 바꾸지 못함을 발견했다 —
      `resize_window`는 "성공"을 반환하지만 `window.innerWidth`로 직접 확인한 결과 375/390/800 등
      어떤 값을 요청해도 실제 뷰포트는 항상 1680×997(브라우저 창이 전체화면으로 고정된 상태)로
      유지되었다(신규 탭으로도 동일 재현 — 창이 공유되어 있어 동일 문제). Playwright MCP는 세션
      전체에서 재연결되지 않아(`ToolSearch`로 재확인 — 서버 연결 실패 유지) 대체 불가능했다. 이로
      인해 홈·상세의 모바일(375)/태블릿(768) **신규** 반응형 스크린샷은 이번 세션에서 물리적으로
      재현하지 못했다. 다만 (1) 두 페이지의 반응형 마크업 자체는 V1(Task 003~005)에서 검증되었고
      이번 V2 작업에서 전혀 수정되지 않았으며, (2) 두 페이지가 공유하는 유일한 변경 컴포넌트인
      `Header`는 Task 016에서 375px 기준으로 `/`·`/admin` 모두 Playwright로 이미 검증되었으므로
      회귀 위험은 낮다고 판단해 이 상태로 결과를 기록한다

## 결과 요약

Task 012~017로 구현된 관리자 영역을 하나의 연속된 여정으로 검증했다: `/admin` 실데이터 목록 →
링크 복사(클립보드 값 정확) → 새 탭 공개 상세(목록과 금액 일치) → PDF 다운로드(V1 회귀 없음, 유효한
PDF 응답)까지 정상 동작을 확인했다. 공개 사용자 여정(홈 → 데모 링크 → 상세 → PDF)도 V1 대비 회귀
없이 정상 동작함을 확인했다.

테스트 도중 두 차례 도구 장애가 있었다: ① PDF 다운로드 버튼 클릭 직후 Playwright MCP 서버 연결이
끊겨 이후 검증을 `curl` 기반 HTTP 레벨 확인으로 전환했다(PDF 응답 유효성, not-found 콘텐츠, 상태
코드). ② 사용자가 Chrome 확장을 재연결해준 뒤 `claude-in-chrome`으로 나머지 여정(관리자 링크 복사·새
탭 이동, 공개 여정 전체)을 실제 클릭 기반으로 재검증할 수 있었으나, 이 확장의 `resize_window`가
이 세션에서 실제 뷰포트를 바꾸지 못하는 별도 제약을 발견했다(항상 1680×997 유지, `window.innerWidth`로
직접 확인). Playwright MCP는 세션 종료 시까지 재연결되지 않았다. 그 결과 홈·상세 페이지의 모바일/태블릿
**신규** 반응형 스크린샷만 물리적으로 재현하지 못한 채 남았다 — 미수정 V1 코드 + Task 016에서 이미
검증된 공유 `Header` 컴포넌트라는 근거로 회귀 위험은 낮다고 판단했지만, 완전한 재확인은 아니었음을
명시해 둔다.

`npm run check-all`·`npm run build` 모두 통과했고, 빌드 라우트 분류(`/admin` 정적+ISR 30초,
동적 라우트들 정상 분류)가 Task 017에서 설계한 캐싱 정책과 일치함을 확인했다.
